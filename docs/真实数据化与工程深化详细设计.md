# 内容风控 Agent 系统：真实数据化 + 调度层改造 + Skill/MCP 大规模工程化 — 详细设计

> 版本：v1.1 ｜ 日期：2026-08-05
> 依据：OutSafe-Bench 真实数据集 + 现有 demo 代码
> 既定决策：内容风控本质是识别违规意图，OutSafe 可直接迭代 demo；
> Skill/MCP 扩至 MCP≥30、Skill≥15；
> **训练侧（LoRA SFT + Agentic RL/GRPO）针对本地开源小模型做**；DeepSeek 大脑（API/开源蒸馏版）不做训练。
> 指标标注：✅ = 有代码/数据支撑的事实；⚠️ = 合理预估待实测，**禁止视为已达成**。

## 0. 总体设计原则与目标架构

### 0.1 设计原则

1. **不破坏现有内容审核路径**：所有新能力以「扩展」实现（新增 mode/节点/工具），默认行为与现状一致。
2. **真实数据优先**：一切量化指标来自 OutSafe-Bench + 补全负样本，不再依赖构造数据集。
3. **降本优先**：LLM 调用是主要成本，新增语义能力一律设计「本地规则预过滤 → 窄口 LLM」漏斗。
4. **可评测即工程**：每个改动点必须挂一个 Track 的可验证指标，无评测不验收。

### 0.2 目标架构（改动后）

```
请求/内容输入
  → Supervisor (L1 确定性分类: 内容类型)            [不变]
  → IntentPreCheck (L2 意图风险预筛)  keyword预过滤 → 本地小模型意图分类(LoRA) → risk_hint
  → Skill/MCP Router: 本地小模型工具选择(Agentic RL) → 动态注入
  → 分支:
      text    → TextAgent (DeepSeek 大脑: 深度推理)  ⤴ 小模型粗判低置信度/高危 → 升级大脑
      image   → ImageAgent ‖ AudioAgent ‖ VideoAgent
      multi   → PlannerNode (确定性5-Phase) → [fallback] TaskPlanner(LLM窄口)
  → route_after_agent (L3 元决策: debate/reflexion/human 增强)
  → RiskAgent → PASS/REVIEW/REJECT
  ↓
本地小模型层 (vLLM): 意图分类 / 工具路由 / 粗判初筛   ← LoRA SFT + Agentic RL(GRPO)
  ↓
Eval Harness v2 (Track 注册制) ← OutSafeLoader + 负样本 + 媒体标注
```

**映射表**（核心设计）：

| 6 False_Information_and_Misderection | `false_info` | 复用现有 |

**涉及文件**：`agent_moderation/constants.py`（新增）、`agents/text_agent.py`（prompt 枚举扩展）、`agents/risk_agent.py`（类型权重）、`eval/datasets/out_safe_loader.py`。
**验证命令**：

### 1.3 审核对象声明：内容审核 vs 请求意图识别

**为什么**：现有 prompt 面向「已发布内容是否违规」；OutSafe 是「用户请求/指令是否含违规意图」（如"查陈小姐银行余额"无任何敏感词，却是隐私侵犯意图）。纯关键词覆盖不到，依赖 LLM 语义，必须让 LLM 明确审核对象是**请求本身**。

**怎么做（同一管线双口径，推荐）**：
- `text_agent.py` 增加 `TEXT_MODERATION_INTENT_PROMPT`：在现 6 维度基础上，新增一条审核对象声明：
  ```
  ## 审核对象
  输入可能是已发布内容，也可能是用户请求/指令。若为请求，需评估请求本身是否包含违规意图：
  诱导获取他人隐私、诱导违法犯罪、传播仇恨歧视、诱导自伤、诱导侵权行为等。
  请求的违规意图与内容违规同等处罚。
  ```
- `TextAgent.process` 与 `get_prompt` 增加 `audit_mode: "content" | "request_intent"` 参数，默认 `content`（**不改线上默认行为**）。
- `moderation.py` 的 `text_agent_node` 从 state 读 `audit_mode`（state 新增可选字段，缺省 content）。

**涉及文件**：`agents/text_agent.py`、`workflows/moderation.py`、`agent_moderation/state.py`（加 `audit_mode: Optional[str]`）。
**验证命令**：同一批 OutSafe 样本，分别跑 `content` 与 `request_intent` 口径，对比 T1 指标，要求 `request_intent` 在隐私/犯罪/健康类 Recall 显著更高（⚠️ 预期 +15pp，需实测）。
**验收**：双口径可切换；`content` 口径下原 T1（构造数据）指标不回退（回归测试）。

### 1.4 安全负样本补全（1,000+ 条）

**为什么**：OutSafe 全部是有害请求，无正常样本 → 只能测 Recall，测不了 Precision/F1/误报率/置信度校准，评测不成立。

**怎么做**：
- 种子：`logs/pipeline.jsonl` 211 条真实请求中 PASS 样本（约 103 条）+ 人工构造。
- 扩写：脚本 `src/backend/scripts/build_safe_dataset.py` 用 LLM 扩写种子为同主题变体（天气/购物/学习/工作/健康咨询/娱乐等 8 类），目标 1,000+。
- 标注：自动标记 `decision=PASS`；人工抽检 10%（100 条）+ LLM 复核全部，剔除误标。
- 落盘：`data/processed/safe_prompts.jsonl`，字段 `{prompt, category, decision, source, difficulty}`。

**涉及文件**：`src/backend/scripts/build_safe_dataset.py`（新增）。
**验证命令**：`python src/backend/scripts/build_safe_dataset.py --count 1200` → 校验条数与抽检率。
**验收**：≥1,000 条 PASS 样本；抽检 10% 无违规内容混入。

### 1.5 多模态标签修复（图片/视频子集预标注）

**为什么**：图片 900 张是 Places365/BigGAN/自然图混合，**多数为中性场景图**，目录≠违规，直接用目录做 ground truth 会大量误标、评测失真。

**怎么做**：
- **图片**：抽 300 张（每类 33）做**预标注集**——LLM（Qwen3-VL）初标「是否违规+违规类型」→ 人工复核不一致项；产出干净标签，仅此子集进 T5 分类评测。
- **剩余 600 张**：作**弱标注**（目录=候选类型），仅用于 T3 RAG 检索（query 侧），不做分类评测。
- **视频 90 个**：全量预标注——抽 3-5 帧 Qwen3-VL + ASR 文本联合判断，人工复核。
- 落盘：`data/processed/out_safe_media_labels.jsonl`（字段：`{media_id, media_type, label, violation_type, source, reviewer}`）。
- 脚本：`src/backend/scripts/label_media_subset.py`（含 VL 标注 prompt + 人工复核清单导出）。

**涉及文件**：`src/backend/scripts/label_media_subset.py`（新增）、`eval/datasets/out_safe_loader.py`（媒体加载分支）。
**验收**：300 图 + 90 视频均有干净标签；双标注不一致率 <10%（⚠️）。

## 2. 子任务 2：全方位 Benchmark（7 Track）

**目标**：EvalHarness 改造成 track 注册制，7 个独立可跑的评测 Track，覆盖识别、对抗、检索、工具、多模态、自进化、成本。

### 2.1 Track 总览

| Track | 目标 | 数据 | 核心指标 | LLM 依赖 |
|---|---|---|---|---|
| T1 意图识别（主） | 9 类有害请求 + 正常识别 | OutSafe 4,600 + 负样本 1,000+ | Acc / Macro-F1 / 各类 P-R-F1 / 混淆矩阵 / ECE / Brier | 是 |
| T2 对抗鲁棒性 | 5 类对抗向量攻击 | T1 子集（每类 50）变换 | 对抗漏检率 / ΔF1 | 是 |
| T3 RAG 检索 | 检索质量四路对比 | OutSafe 弱标注 case 库 | Recall@k / MRR / NDCG@k / Hit@k | **否（本地）** |
| T4 Skill/MCP 调用 | 工具选择与注入有效 | 工具选择测试集（构造） | 工具选择 Acc / Skill Hit@k / 注入 Δ | 部分 |
| T5 多模态 | 图/视频违规判定 | 预标注 300 图 + 90 视频 | 图片 P-R-F1 / 视频帧级 F1 | 是 |
| T6 Agent 链路+自进化 | 完成率 / 迭代提升 | T1 子集 | 多轮完成率 / ΔF1 / A/B 有效 / 回滚率 | 是 |
| T7 成本与延迟 | 工程开销 | 全量抽样 | p50/p95 / token / LLM 次数 / 工具次数 | 否 |

### 2.2 关键指标定义与公式

- **Macro-F1**：每类 F1 的算术平均（跨类混淆分析基于混淆矩阵逐类展开）。
- **ECE（Expected Calibration Error）**：按置信度分 10 桶，`ECE = Σ(b_n/N) · |acc(b_n) − conf(b_n)|`。✅ 有 confidence/risk_score 输出可算。
- **Brier Score**：`(1/N)Σ(conf_i − y_i)²`，y_i∈{0,1}。
- **对抗漏检率**：原判定拦截（REJECT/REVIEW）经对抗变换后变为 PASS 的比例。
- **Recall@k / MRR / NDCG@k / Hit@k**：标准信息检索定义，query 为 OutSafe prompt，gold 为同类别历史 case（弱标注），四路对比（纯向量 / BM25 / Hybrid / Hybrid+CrossEncoder）。⚠️ 预填值 Recall@10：纯向量 ~0.6 → Hybrid+CE ~0.8（需实测，见 6.3 可先跑）。
- **工具选择准确率**：`工具选择正确数 / 总数`，gold 由测试集给定。
- **注入有效性 Δ**：`注入 Skill 后的判定 F1 − 不注入 F1`（同一批样本）。

## 3. 子任务 3：Supervisor / Planner 调度层改造

**目标**：三层调度——L1 确定性粗分类（不变）、L2 新增意图风险预筛（语义）、L3 复杂路由元决策（按需 LLM）；Planner 规则表为主 + LLM fallback 窄口。

### 3.1 现状确认（代码事实）

- `supervisor_node` → `SupervisorAgent._identify_content_type`：确定性内容类型分类（text/image/audio/video/multi），**不调 LLM** ✅。
- `planner_node`（`moderation.py`）：**Planner v4.0 确定性 5-Phase 编排**，docstring 明确"固定路线, 0 LLM 调度开销" ✅。
- `agents/planner.py`：`TaskPlanner v2.0`——**LLM 驱动的 ReAct Plan-and-Execute**（THINK→ACT→OBSERVE→REPLAN），已有资产，当前用于复杂任务（react_agent），**可复用为 LLM fallback 窄口** ✅。

### 3.2 L1 确定性粗分类 —— 保持

**结论**：输入类型分类基于元数据/文件头，确定性强，LLM 零增益 + 引入延迟与不可控。**不改**。
**收益/成本**：成本 0；维持现有毫秒级延迟。

### 3.3 L2 意图风险预筛（新增）—— 降本漏斗 + 窄口 LLM

**为什么**：OutSafe 引入的语义维度（请求意图）在 keyword 层无信号（"查银行余额"无敏感词）。若不走语义预判，这类高危请求会被当低风险走浅审核。**结论：此层需要 LLM（或小模型）**，但必须降本。

**怎么做（两级漏斗）**：

```
IntentPreCheck (新增 intent_precheck_node, 挂 supervisor 之后)
  L2a 本地 keyword 预过滤: AC自动机命中高危词 → 直接 risk_hint=high, 不调 LLM
  L2b 未命中 → 窄口 LLM 意图预判: 单次调用, 输出 {intent_risk: none/low/high, category_hint: [1-9]}
  → state["_intent_precheck"] = {risk_hint, category_hint, llm_called}
```

- 复用 `agents/text_agent.py` 的 DeepSeek 客户端，专用轻 prompt（无 reasoning 长文，max_tokens≈100，温度 0）。
- `route_after_agent` / `route_to_debate` 消费 `risk_hint`：high → 强制走 debate/reflexion；low 且判定 PASS 但 `category_hint` 存在 → 提升到 REVIEW。
- **本地小模型**：L2b 的窄口用本地小模型（Qwen2.5-1.5B/3B LoRA 微调意图分类）替代 API——详见子任务 5；API LLM 仅作 fallback。

**涉及文件**：`workflows/moderation.py`（新增节点 + 边）、`agent_moderation/agents/intent_precheck.py`（新增）、`state.py`（`_intent_precheck` 字段）、`route_after_agent/route_to_debate`（消费 risk_hint）。
**验证命令**：对 T1 中 keyword 无命中的子集（构造：OutSafe 随机抽 100 条筛掉含敏感词者）跑 L2，统计 `llm_called` 占比与 risk_hint 命中率。
**收益/成本论证**：收益 = 高危意图不漏（T1 隐私/犯罪类 Recall）；成本 = 仅在无敏感词时才 1 次 LLM 调用（预计 <20% 流量，⚠️ 需实测）。

### 3.4 L3 复杂路由元决策 —— 按需 LLM，窄口

**现状**：`route_after_agent`（react/debate/reflexion）、`route_to_debate`（debate/human/risk）已存在，阈值驱动。
**增强（窄口 LLM 元决策）**：当 `risk_hint=high` 或置信度落在 `(0.3, 0.7)` 且各 Agent 意见不一致时，调 1 次 LLM 判断"该走 debate、升级 human，还是直接 risk"（max_tokens≈80）。其余情况保持确定性路由。
**失败模式与回退**：LLM 元决策超时/出错 → 回退到确定性阈值路由（现状行为），不改图结构。

### 3.5 Planner「规则表为主 + LLM fallback 窄口」

**结论**：`planner_node` 确定性 5-Phase **保留为主**；新增 **fallback 到 `agents/planner.py`（TaskPlanner，LLM 驱动）** 作为窄口。

**触发条件（任一）**：
1. `content_type` 或文件 mime 类型不在规则表（新增类型，如压缩包、直播流）。
2. 确定性 phase 抛错或超时（>30s）。
3. 跨模态冲突强信号（图文矛盾，现有 `_fusion_result` 标记）需要 Plan-and-Execute 深潜。

**实现**：`planner_node` 包 `try/except` + 前置表查询，未命中或异常时 `state["_planner_fallback"]=True`，路由到 `agents/planner.py` TaskPlanner 的执行入口。
**收益/成本**：确定性路径覆盖 95% 常规组合（0 开销）；fallback 只在非常规时花 LLM token，换取能力边界扩展。

**涉及文件**：`workflows/moderation.py`（fallback 分支）、`agents/planner.py`（复用，可能加约束）。
**验收**：常规多模态走确定性路径（pipeline 日志无 TaskPlanner 调用）；构造一个规则表外场景（如空文件类型）触发 fallback 成功。

### 3.6 子任务 3 风险与回退

| 风险 | 应对 |
|---|---|
| L2 误伤正常请求 | risk_hint 只影响"是否升级审核"，不直接 REJECT；负样本评测兜底 |
| fallback 无限循环 | TaskPlanner 已有 MAX_STEPS=8，超时回退确定性路径 |
| 延迟上升 | 每层都设窄口（<20% 流量）+ 缓存 |

### 4.2 Skill 向量化语义路由（核心升级）

**为什么**：现状 `skill_registry.find_by_mcp_tool / find_by_content_type` 是**注册表匹配**——query 换了说法就召回不到。语义路由把匹配从"标签相等"升级为"语义相似"。

**怎么做**：
- 复用 `bge-small-zh-v1.5`（HybridRetriever 已有），把每个 Skill 的 `description + tags + triggers + mcp_tools` 拼成文本 → 嵌入 → 建索引（新 ChromaDB collection `skill_index` 或内存 FAISS）。
- 新增 `agent_moderation/skill_router.py`：

```python
class SkillRouter:
    def route(query: str, top_k=3) -> list[(skill_name, score)]
        # query 嵌入 → 余弦相似度 top-k
        # 与 rule 匹配(frontmatter tags/content_type)做加权融合: 0.6*语义 + 0.4*规则
def get_skill_router() -> SkillRouter
```

- 语义命中后仍走原 `SkillRegistry.get_skill(name)` 取 L2 内容（复用现有加载/缓存/激活统计）。
- 对齐思路：HuggingGPT / Gorilla / ToolLLM 的 function routing（统一 Router 输出 `(skill, tool)` 联合排序），但**本期用 embedding 而非 LLM router**（降本，效果足够）。

**涉及文件**：`agent_moderation/skill_router.py`（新增）、`skill_registry.py`（扩展 `find_by_query`，保持旧接口兼容）、`memory/chroma_service.py`（新 collection）。

### 4.3 动态上下文注入（防上下文溢出）

**为什么**：15+ Skill 全文全注入会爆上下文、稀释注意力。三层渐进加载需强化为「按需」。

**设计**：

```
Agent system prompt 组装（每 Agent）:
  L1 常驻: 语义路由命中的 top-k Skill 元数据 (name+1行description, ~100 token/个)
           budget 上限 = 3 个 / 500 token
  L2 按需: Agent 决定调用某工具时, 才注入该工具绑定 Skill 的全文
           (首次调用注入, 之后会话内保留)
  L3 按需: references/scripts 文件仅在显式需要时注入
```

- 新增 `SkillContextBudget`（`skill_registry.py` 或独立类）：per-agent 累计注入 token 统计 + 超预算时的截断/压缩（取指令前 80%）。
- `get_skill_context` 增加 `max_tokens` 参数，支持截断。
- 量化：T4 记录 `注入 token 数` 与 `判定 F1`，验证「动态注入 token 节省 + 效果不降反升」。
  ⚠️ 预期：相比全量注入，token 节省 60%+，F1 持平或 +2pp（需实测）。

**涉及文件**：`skill_registry.py`（budget/截断）、`agents/base.py`（prompt 组装入口，注入路由结果）、`agent_moderation/skill_router.py`。

## 5. 子任务 5：小模型延伸架构（DeepSeek 大脑 + 本地小模型，LoRA + Agentic RL）

**目标**：构建「开源 DeepSeek 大脑（深度推理/裁决）+ 本地小模型（高频结构化前置任务）」两级架构；小模型经 **LoRA SFT** 学会任务，再经 **Agentic RL（GRPO）** 强化决策策略；可插拔推理路由层。

### 5.1 架构定位与分工原则（结论先行）

**不做「全量 DeepSeek 开源版本地部署」**：DeepSeek 主力开源版（V3/R1，约 671B MoE）单机不可行，这是算力事实，不画饼。

**现实两级架构**：

| 层 | 承担 | 模型 | 路径 |
|---|---|---|---|
| **大脑** | 深度推理、6 维审核 reasoning、最终裁决、复杂跨模态 | DeepSeek API（可切换本地蒸馏版 DeepSeek-R1-Distill-Qwen-7B/14B） | 慢路径 |
| **延伸** | 意图分类、工具路由、粗判初筛（高频/结构化/可验证） | 本地小模型 Qwen2.5-1.5B/3B/7B（LoRA 微调 + Agentic RL） | 快路径 |

**分工判断准则**（每个任务照此过一遍）：
1. 输出为**固定枚举/结构化 JSON** → 小模型
2. 需要**深度多步推理 / 长 reasoning**（审核 200-500 字）→ 大脑
3. **延迟敏感且流量大** → 小模型（快路径）
4. **判定错误成本高**（最终裁决）→ 大脑兜底；小模型只产预筛/升级信号，不产终局

### 5.2 小模型应用场景判断表

| 任务 | 小模型? | 方式 | 判断理由 |
|---|---|---|---|
| L2 意图风险预筛（9 类+normal） | ✅ **主场景** | LoRA 分类 + GRPO 校准 | 固定枚举；OutSafe 4,600 + 负样本 1,000 标注齐 |
| Skill/MCP 路由（工具选择） | ✅ **主场景** | LoRA 工具调用 + Agentic RL | action 空间 = 35 工具，可验证；ToolBench/Gorilla 范式 |
| 文本粗判初筛（疑似/正常二分类） | ✅ | LoRA 二分类 | 降本：疑似才升级大脑，快路径兜底 |
| 敏感词/正则预过滤 | ❌ | AC 自动机 | 确定性，模型零增益 |
| 核心审核判定（6 维 reasoning） | ❌ | DeepSeek 大脑 | 深度推理 + 可解释性要求 |
| 图文/跨模态冲突初筛 | 半 | VL 小模型初筛 | 复杂，v2 优化项 |
| 最终裁决 / 风险融合 | ❌ | 规则 + 大脑 | 错误成本高，稳优先 |
| 对抗文本检测（变换识别） | 半 | 规则为主 + 小模型 | 复用 `adversarial_detect` 规则 |

### 5.3 LoRA 微调（SFT）方案

**原则**：先 SFT 后 RL（对齐 DeepSeek-R1 训练范式）；LoRA rank=16 / alpha=32，target 覆盖 q/k/v/o。

| 模型 | 任务 | 训练数据 | 输出 | 框架 |
|---|---|---|---|---|
| Qwen2.5-1.5B-Instruct | 意图分类（10 类） | OutSafe 4,600 + 负样本 1,000 | `{category, confidence}` | LlamaFactory / TRL |
| Qwen2.5-3B-Instruct | 工具选择 | `tool_selection_test.jsonl` 600 | `{tool, params}` JSON | LlamaFactory |
| Qwen2.5-3B-Instruct | 文本粗判（二分类） | OutSafe 子集 + 负样本 | `{suspect, confidence}` | LlamaFactory |
| DeepSeek-R1-Distill-Qwen-7B | 本地大脑（可选） | 不微调，仅 4bit 量化部署 | — | — |

> **12GB 显存约束**：意图模型（1.5B）是**唯一 Agentic RL 主战场**；工具路由 3B 只做 SFT，如也要 RL 则降 1.5B；7B 一律不训练（量化部署可）；粗判模型从 7B 降为 3B。

数据格式：`{instruction, input, output}`，output 严格 JSON（对齐审核管线解析）；SFT 用 QLoRA（4bit）以降低显存。
**验收**：意图模型在 T1 子集 F1 与 API DeepSeek 差距 <3pp（⚠️）。

### 5.4 Agentic RL（GRPO）方案

**为什么 GRPO**：判定对错 = OutSafe ground truth 可验证（deterministic verifier），group relative advantage 不需 critic，比 PPO 简单稳定，训练开销适配 7B 级。

**优化对象与 reward（两处强化）**：

**(a) 意图识别强化（L2）** — policy：LoRA-SFT 后的 Qwen2.5-1.5B
```
action: (decision, category, confidence) 三元组
R = +1.0×(决策对) + 0.5×(类别对) − 0.5×(类别错) − 1.0×(漏判)
    + 0.3×(1 − |confidence − correctness|)     # 校准项
安全不对称: 漏判惩罚权重 = 2× 误判（内容风控业务约束）
数据: OutSafe 训练子集（每类 50 ≈ 450 条）+ 负样本
```

**(b) 工具调用强化（Skill/MCP Router）** — policy：LoRA-SFT 后的 Qwen2.5-3B
```
action: ReAct 工具调用轨迹（选工具 + 参数）
R = +1.0×(工具选择对) + 0.3×(参数对) − 0.1×(冗余调用) − 0.05×λ×(LLM调用次数)
数据: tool_selection_test.jsonl 拆 train/val
```

**训练流程**：SFT(LoRA) → GRPO 2-3 轮（batch 8-16）→ 冻结 → vLLM 部署 → 与 API baseline 对比评测。
**框架**：TRL `GRPOTrainer` / veRL。

**显存需求（估算 ⚠️，受 batch/seq_len/group_size 影响）**：

| 模型 | vLLM 部署 | LoRA SFT (bf16) | QLoRA SFT (4bit) | GRPO |
|---|---|---|---|---|
| Qwen2.5-1.5B | 3-4 GB | 8-10 GB | 4-6 GB | 12-16 GB |
| Qwen2.5-3B | 6-8 GB | 12-16 GB | 6-8 GB | 20-28 GB |
| Qwen2.5-7B | 15-18 GB | 28-36 GB | 10-14 GB | 32-48 GB（降 group_size 可至 24） |

- 假设：batch=4、seq≤1024、gradient checkpointing 开启、GRPO group_size=8、LoRA rank=16。
- **本机 12GB（RTX 3060/4070 档，当前约束）**：
  - ✅ 1.5B/3B 的 QLoRA SFT（4-8 GB）；vLLM 部署 1.5B/3B（7B 4bit 也可）。
  - ✅ **1.5B GRPO**（唯一 RL 场景）：必须压参数，见下。
  - ❌ 3B GRPO、7B 任何训练、7B QLoRA SFT（临界 10-14GB，不推荐）。
  - **1.5B GRPO 在 12GB 下的强制参数**：
    ```
    QLoRA 4bit 基座 + LoRA(rank=16)
    per_device_train_batch_size=1 / gradient_accumulation_steps=4
    max_seq_length=512 / GRPO group_size=4
    gradient_checkpointing=True / optimizer=paged_adamw_8bit
    ```
    按此配置 1.5B GRPO 实测约 10-12 GB。3B 想碰 RL 唯一出路是 offload（体验差，不推荐）。
- **更大规模 RL（如 7B 粗判强化）**：本地 12GB 开发，真训时租卡（RTX 4090 ≈ ¥1.5-2/时）按需租用。
- GRPO 显存大头来自「policy+reference 双模型 + 整组 rollout 同时生成」，这是 SFT 的 2-3 倍。
