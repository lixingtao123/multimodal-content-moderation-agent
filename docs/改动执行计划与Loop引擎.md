# 改动执行计划与 Loop 引擎

> 版本：v1.0 ｜ 日期：2026-08-06
> 依据：《最终详细设计-秋招项目版.md》(v1.0)。本文件 = 改动计划的执行版 + 开发治理机制 + 总指挥提示词。
> 核心原则：**边开发、边测试、边审查**；**禁止编造、禁止美化、禁止跳过未实现模块**。

---

## 0. 结论（TL;DR）

- 改动分 **P0-P9 十个阶段**，拆成 **18 个可独立验收的轮次（R0-R18）**，每轮都是「规划→开发→单测→审查→校验→汇报」的完整循环。
- 验证分 **四级（L0-L4）**：静态 → 单元 → 集成 → 评测/E2E。
- 质量门 **G0-G4**：每块单测绿 → 每轮集成绿 + track 不回归 → 阶段基准不回归 → 全量 + 前端逐页 E2E。
- **前端零测试基建是已知缺口**，E2E 用「tsc + build + 每页功能点清单逐项核对 + API 联调」实现，组件测试（vitest）作为可选加固。
- 每轮结束强制输出**轮次报告**，明确标注：改了什么 / 测试结果 / **遗留问题（占位/未实现必须显式标注）**。

## 2. 验证体系

### 2.1 四级验证（L0-L4）

| 级 | 验证内容 | 工具/命令 | 触发时机 |
|---|---|---|---|
| L0 | 静态检查：语法/类型/风格 | 后端 `ruff check .`；前端 `tsc --noEmit` | 每块改动后 |
| L1 | 单元测试（块级） | `pytest tests/unit` | **每改一块必跑** |
| L2 | 集成测试（模块级） | `pytest tests/integration src/backend/tests` | 每轮校验时 |
| L3 | Benchmark 评测（track 级） | `harness_v2 run`（7 Track） | 阶段末 + 全量 |
| L4 | 端到端测试（前端逐页 + API 全链路） | 见 §5 功能核对清单 | R18 + 最终 |

### 2.2 质量门（G0-G4）

| 门 | 名称 | 通过条件 | 不通过怎么办 |
|---|---|---|---|
| G0 | 环境门 | pytest/ruff/tsc 可运行，依赖齐全 | 先修基建，不进入任何改动 |
| G1 | 块级门 | 每个改动块有单测且全绿 | 该块不得进入下一块开发 |
| G2 | 轮级门 | 本轮集成测试全绿 + 相关 track 相对 baseline 不回归 | 当场纠错，修复后再过门 |
| G3 | 阶段门 | 阶段末全量相关测试 + 该阶段涉及 track 对比 | 修复或回滚，**绝不许带病前进** |
| G4 | 发布门 | 7 Track 全绿 + 前端逐页 E2E + 总结报告 | 未全绿不宣布完成 |

## 3. Loop 引擎机制

### 3.1 每轮标准流程（一个 Round）

```
┌────────────────────────────────────────────────────┐
│  Round N: [阶段] - [本轮改动块]                        │
│                                                    │
│  ① 规划   列出改动块清单 + 每块单测方案 + 验收门槛        │
│  ② 开发   按块小步实现（一块一停，不积压）               │
│  ③ 单测   每块写完立即跑 L1 单测，绿才进下一块（G1）      │
│  ④ 审查   代码审查：断点/占位/编造/逻辑漏洞（§4 纪律）    │
│  ⑤ 校验   跑 L2 集成 + 相关 track 对比 baseline（G2）    │
│  ⑥ 汇报   输出轮次报告（改什么/测试结果/遗留/下一轮）      │
└────────────────────────────────────────────────────┘
```

### 3.2 跨轮机制

- **回归护栏**：baseline.json（R5 固化）是后续所有轮次的对比基准；每轮 track 对比只允许「不回退 + 目标指标变好」。
- **纠错闭环**：任一质量门失败 → 冻结后续开发，先定位修复 → 复跑该轮校验 → 通过才继续。
- **阶段卡点**：P0-P2 每阶段结束跑一次 G3；P3 之后每两轮跑一次 G3。
- **断点专查**：每轮审查固定检查「看起来在但实际没接上」的模块（对标 F1 HITL 案例），这是本项目历史问题的最大来源。

---

## 4. 审查纪律（禁止项）

1. **禁止编造**：所有指标必须实测。测试没跑过就不许报数字；设计文档中的 ⚠️ 必须实测后转 ✅。
2. **禁止跳过**：任何模块只要未实现 / 功能不完善 / 逻辑不对 / 没真正发挥作用，必须**显式标注「占位/未实现/待验证」**，不许混入「已完成」汇报。
3. **禁止美化**：测试失败如实贴失败输出；功能不通如实说明断在哪一层（前端/API/工作流）。
4. **断点专查**：每轮审查专门找「两端齐全中间断路」类问题（如 F1：API 与前端都在、工作流无入边）。
5. **验收对应**：每个改动点必须能在汇报里指出「对应哪条测试证明它生效」，拿不出测试证明的一律视为未完成。

## 5. 前端功能核对清单（E2E 模板）

前端**无测试基建**（无 vitest/playwright）——这是已确认的现状。E2E 按三层执行：

- **L0 构建**：`tsc --noEmit` + `vite build` 必须通过。
- **API 联调**：对照 `api/client.ts`，每页每个功能点调用真实后端 API，验证数据流闭环。
- **功能点核对**：逐页逐功能点填表，见下。

### 5.1 现有页面核对清单

| 路由 | 页面 | 功能点（逐项核对） |
|---|---|---|
| /dashboard | Dashboard | 统计卡数值真实、图表渲染、Benchmark 入口卡（新增） |
| /moderate | ModerationPanel | 内容类型切换、审核提交、tier 路径展示（新增）、plan 摘要（新增） |
| /async | AsyncModeration | 任务创建、状态轮询、结果回填 |
| /review | HumanReviewPanel | **pending 列表有数据（F1 修复后）**、通过/拒绝操作、关联案例（新增）、提交后状态变化 |
| /optimization | OptimizationMonitor | 自进化事件、优化记录、指标图表 |
| /history | HistoryList/Detail | 列表、详情、推理链 |
| /system | SystemMonitor | 组件健康、指标 |
| /lab | TechLab | prompts/tools/skills 三区、工具调用 |
| /policies | PolicyManager | 策略 CRUD、生效 |

### 5.2 新增页面核对清单

| 路由 | 页面 | 功能点 |
|---|---|---|
| /benchmark | Benchmark 报告 | Track 结果表（vs 基线涨绿跌红）、趋势图、重跑按钮调 evaluation API |
| /skills | Skill/Tool 管理 | manifest 列表、质量分、灰度状态、新增注册 |
| /dataset | 数据集管理 | OutSafe 导入进度、标注状态、负样本统计 |

> 模板：每个功能点一行，列 `功能点 | 触发操作 | 期望结果 | 实测结果 | 状态(✅/❌/占位)`。**❌ 和「占位」必须进遗留问题清单，不许隐藏。**

## 6. 总指挥提示词（Master Prompt）

> 用途：粘贴给 loop engine / 子 agent / 新会话，作为整轮开发的唯一指挥指令。每轮只需把「本轮内容」替换为轮次表对应行。

```
【角色】
你是内容风控智能治理系统的资深开发 + 审查专家。这是字节「大模型应用算法 + Agent 开发」秋招项目。
当前以《最终详细设计-秋招项目版.md》为唯一蓝图，执行版本化改造。改造总原则：现有功能全部保留，接线、补链、增强，不推倒重来。

【本轮任务】
（粘贴轮次表中本轮内容：阶段、改动块、验收门槛）

【硬约束】
1. 全程中文交流，结论先行再给理由；思考过程用中文；代码、变量名用英文。
2. 12GB 显存约束：不做模型训练/RL。训练相关只做「接口按可训练设计 + 数据准备」，绝不虚报"已做训练/RL"。
3. 模拟案例不删除：RAG 案例库中 source=simulated 的旧数据必须保留，真实数据以 source=out_safe 并行灌入，检索按来源加权（confirmed>out_safe>simulated>model_labeled）。
4. 密钥/token/密码不进代码、不进 commit。
5. 每个改动必须先有方案，方案变动前先说清楚。

【开发纪律（边开发边测试）】
1. 每改动一个块（函数/类/文件级），立即写或更新该块单元测试并跑绿（L1），一块一验，不许攒批。
2. 完成一个大模块（如整个编排层、整个工具层）后，跑模块集成测试 + 相关 benchmark track（L2/L3）。
3. 全部改动完成后，跑全量 7 Track 回归 + 前端每一页功能逐一验证（L4，§5 清单）。
4. 整个过程按轮次执行；每轮结束跑一次校验，发现错误当场修复再进下一轮。
5. 行为变化必须由测试证明。"我觉得应该没问题"不算验证。

【审查纪律（禁止编造/美化/跳过）】
1. 禁止编造：所有指标必须实测，没跑过就不许报数字；⚠️ 指标实测后转 ✅，未实测保持 ⚠️。
2. 禁止跳过：未实现/不完善/逻辑不对/没真正发挥作用的模块，必须显式标注「占位/未实现/待验证」，不许混入已完成汇报。
3. 禁止美化：测试失败如实贴输出；功能不通如实说明断在哪一层（前端/API/工作流）。
4. 断点专查：每轮审查专门找"两端齐全中间断路"类问题（对标 F1：API 与前端都在、工作流无入边）。对每个"看起来存在"的模块，必须确认它真的被调用、真的有入边。
5. 每个改动点必须在汇报中指出"哪条测试证明它生效"；拿不出测试证明的一律视为未完成。

【每轮循环流程】
① 规划：列出本轮改动块清单 + 每块单测方案 + 验收门槛。
② 开发：按块小步实现。
③ 单测：每块写完立即跑该块 L1 单测，全绿才进下一块。
④ 审查：按审查纪律做代码审查。
⑤ 校验：跑 L2 集成 + 相关 track 对比 baseline.json，检查回归。
⑥ 汇报：输出轮次报告。

【轮次报告格式】
- 改动清单（文件路径 + 内容摘要）
- 测试结果（跑了哪些、结果、失败输出原文）
- 遗留问题（未实现/占位/待验证的，逐条列出，禁止隐藏）
- 下一轮计划
- 每个改动的测试证明（改动点 ↔ 测试用例对应关系）

【前端 E2E（全部改完后执行）】
从 /dashboard 到 /policies 以及新增 3 页，逐页核对：
1. 类型检查 + 构建通过（tsc --noEmit + vite build）。
2. 每个功能点对应的后端 API 真实连通（对照 api/client.ts）。
3. 新增页面数据流闭环。
4. 输出每页核对表（功能点 | 操作 | 期望 | 实测 | 状态）。
5. ❌ 和「占位」进遗留问题清单，修复后才宣布完成。
```

## 7. 执行顺序说明

1. **先 R0**：不跑绿现有测试、不确定基线，不进入任何改动——这是 G0 环境门的硬要求。
2. **R1-R5（P0+P1）** 是全局地基：数据真实化 + 评测体系，后面所有阶段的验收都依赖这两块。
3. **R8（E4 HITL）** 是优先级最高的单项修复：前后端已就位、只补工作流接线，改动小、故事性强、验收直观（人工审核面板第一次能见到真实数据）。
4. **R18** 必须全绿才宣布项目完成；任何遗留问题写进报告，不掩盖。
