## 1. 这个项目是做什么的？

**一句话说**：这是一个运行在你自己电脑上的"AI 内容审核中台"。

它能够自动检测文本、图片、音频、视频中是否包含违规内容：

| 功能 | 大白话解释 |
|------|-----------|
| **文本审核** | 你输入一段文字，系统告诉你有没有敏感词、骂人、广告、诈骗等内容 |
| **图片审核** | 你上传一张图，AI 看图判断是否违规（色情/暴力/广告等），还会提取图中的文字 |
| **音频审核** | 你上传一段语音，系统先转成文字，再检测文字是否违规 |
| **视频审核** | 你上传视频，系统抽取关键帧逐帧分析，同时分析音频轨道 |
| **多模态审核** | 上传文档（含图文）+图片+音频，系统自动编排 13 个 AI 节点协作分析 |
| **策略管理** | 运营人员可以调阈值（多少分算违规）、管敏感词库，改了立即生效 |
| **自动标注** | 每条审核完自动"二审"，发现错误记录下来 |
| **自动优化** | 错误攒够了自动分析原因，改进 Prompt，像有质检员和培训师在不断优化 |
| **技术实验室** | 开发人员可以看到完整审核流程图、调试 Prompt、查看工具调用记录 |

**这些功能背后有 13 个 AI 节点在协同工作**——包括 DeepSeek 大语言模型做语义理解、Qwen3-VL 视觉模型看图、FunASR 做语音转文字等。

## 3. backend 目录详解（后端代码放哪）

后端就是"服务器"——它接收网页发来的请求，处理数据，返回结果。所有后端代码在 `src/backend/` 目录下。

### 3.1 项目启动入口文件

```
src/backend/main.py    ← 整个项目的"开关"
```

当你执行 `python -m src.backend.main` 时，这个文件会：
1. 读取 `.env` 配置文件
2. 连接 PostgreSQL 数据库
3. 连接 Redis 缓存
4. 连接 ChromaDB 向量数据库
5. 如果 ChromaDB 是空的，自动导入示例数据
6. 恢复 GraphRAG 知识图谱状态
7. 启动后台任务工作池（3 个并发 worker）
8. 启动后台标注消费者（3 个并发 worker）
9. 启动 Web 服务器，等待请求

控制台会打印类似这样的信息：

```
[Init] Database connected (PostgreSQL)
[Init] Redis connected
[Init] ChromaDB connected
[Init] GraphRAG state restored
[Worker] TaskWorkerPool started (3 workers)
[Annotation] Consumer pool started (3 workers)
Server started on http://0.0.0.0:18080
```

看到 `Server started` 说明启动成功了。

### 3.2 API 接口层 — src/backend/api/

这是**前端和后端通信的桥梁**。

```
src/backend/api/
├── __init__.py
├── websocket.py                 ← WebSocket 实时推送审核进度
└── routes/
    ├── moderation.py            ← 核心审核接口（文本/图片/音频/视频/多模态提交）
    ├── async_moderation.py      ← 异步任务接口（提交→轮询→取结果）
    ├── query.py                 ← 结果查询 + 历史记录分页
    ├── admin.py                 ← 管理后台（统计/健康/标注/优化报告）
    ├── policies.py              ← 策略管理 CRUD（敏感词/阈值/权重）
    ├── tech.py                  ← 技术实验室（管线图/RAG/Prompt/Skills/MCP）
    ├── mcp.py                   ← MCP JSON-RPC 2.0 端点
    ├── evaluation.py            ← 评估接口（LLM-as-Judge / RedTeam）
    └── logs.py                  ← 日志查询接口
```

**大白话解释**：
- `routes/` 下的每个文件对应一类功能。前端网页点"提交审核"按钮，就会调用 `moderation.py` 里的代码。
- `policies.py` 定义了策略管理的数据格式——敏感词存哪些字段、阈值怎么配置。
- `websocket.py` 让前端能实时看到审核进度（不用反复刷新页面）。

#### Agent 工作流（便于理解 13 个节点的协作）

```
用户提交"文档+图片+音频" →
  Supervisor（识别为 multi_modal）→
  Triage 分诊台（非文本 → 默认 med 标准车道）→
  Planner（5 阶段编排）：
    P1: FileAgent（解析文档，提取文字和嵌入图）→
    P2: ImageAgent×21 ‖ AudioAgent×1（图片和音频并行分析）→
    P3: 图片判定按位置插回 + ASR转写 → 融合文本 → TextAgent（统一语义分析）
        （OCR 段单独收集，不拼入融合文本，仅统计+跨模态关联）→
    P4: 跨模态关联（图文矛盾/互证/OCR关联/音频关联）→
    P5: 输出结果→
  RiskAgent（内嵌意见协商 + 综合评分 → PASS/REVIEW/REJECT）
```

#### 每个 Agent 的大白话解释

| Agent | 大白话解释 |
|-------|-----------|
| `supervisor.py` | 组长。每条审核都先经过它，看一眼类型，分配给对应的组员 |
| `file_agent.py` | 档案员。有人上传了文档（PDF/DOCX），它拆解文字和嵌入图片 |
| `text_agent.py` | 文字专家。检测敏感词、理解语义、查历史案例。最忙的 Agent |
| `image_agent.py` | 图片专家。用 AI 看图、提取图中文字（OCR）、检测相似图 |
| `audio_agent.py` | 音频专家。语音转文字（ASR）、识别说话人、审核转写文本 |
| `video_agent.py` | 视频专家。抽帧→逐帧看图→提取音频轨道→综合分析 |
| `debate_panel.py` | (已合并) 辩论逻辑并入 RiskAgent 意见协商（加权投票） |
| `reflexion.py` | (已合并) 反思逻辑并入 ReAct 第二阶段（自校准） |
| `react_agent.py` | 高级侦探。文字专家拿不准时（置信度低），多步推理深挖 |
| `risk_agent.py` | 终审法官。综合所有专家的意见，做出最终判定 |
| `planner.py` | (旧版备份) 用 LLM 决定调度顺序。已被 Planner 固定 5 阶段路线替代 |

    ├── keyword_check.py ← AC 自动机敏感词检测（纯本地，~1ms）
    ├── history_search.py← BM25+Dense+CrossEncoder 混合检索
    ├── image_hash.py    ← dHash 相似图片检测（64bit 指纹 + 汉明距离）
    ├── account_risk.py  ← 账号历史违规记录查询
    ├── adversarial_detect.py ← 对抗文本检测（同音字/拆字/混淆）
    ├── url_check.py     ← 恶意 URL/钓鱼链接检测
    ├── content_dedup.py ← MD5 内容去重（Redis 缓存）
    └── regex_rule.py    ← 正则规则（手机号/银行卡/黑话）
```

**大白话解释**：
- **AC 自动机（keyword_check）**：一种极快的文本匹配算法，扫一遍 10 万字只需几毫秒。
- **dHash（image_hash）**：把图片缩成 8×8 的缩略图，比较相邻像素的明暗，生成 64 位的"指纹"。两张图的指纹差异（汉明距离）越小，越可能是同一张图。
- **MCP 协议**：Anthropic 提出的 AI 工具调用标准，就像 USB 是设备连接标准一样，MCP 是 AI 和工具的连接标准。

### 3.5 记忆系统 — src/backend/memory/

这是 Agent 的"记忆"和"知识库"。

```
src/backend/memory/
├── manager.py           ← 分层记忆管理器（协调 Redis + ChromaDB）
├── agent_memory.py      ← MemGPT 风格三层次记忆
│                           Core(PostgreSQL, 重要性>0.7, 永久)
│                           Working(Redis, 1h TTL, 当前会话)
│                           Archival(ChromaDB, 低权重, 可检索)
├── agentic_rag.py       ← 智能检索循环（改写→路由→检索→自评, 最多3轮）
├── multimodal_rag.py    ← CLIP 以图搜图（512维视觉特征→ChromaDB）
├── graph_rag.py         ← 违规知识图谱（NetworkX BFS 2跳扩展）
├── hybrid_retriever.py  ← BM25+Dense(BGE-M3)+CrossEncoder→RRF融合
├── chroma_service.py    ← ChromaDB 操作（BGE-M3 嵌入, 多级回退）
└── redis_service.py     ← Redis 操作（短期记忆/任务队列/LLM缓存/去重）
```

**大白话解释**：
- **三层记忆**：像人脑一样——重要的事情记在"核心记忆"（PostgreSQL，永久），正在处理的放在"工作记忆"（Redis，1小时后自动忘），不太重要的归档（ChromaDB，可以搜索但权重低）。
- **RAG（检索增强生成）**：AI 回答问题前先去"档案室"查资料，再回答。这样回答更准确。
- **CLIP 以图搜图**：把图片转成 512 个数字（向量），在向量库里找最相似的图。

### 3.6 标注与优化系统 — src/backend/optimization/

这是让系统**越用越准**的"质检 + 培训"体系。

```
src/backend/optimization/
├── annotation_agent.py  ← ★ 标注 Agent
│                           ① 规则引擎复核（6大类77关键词, ~1ms）
│                           ② 快速跳过（规则与模型一致→省LLM开销）
│                           ③ LLM独立审核（不同prompt+temperature）
│                           ④ 语义矛盾检测（violation_type vs reason）
│                           ⑤ 三方投票（规则+LLM+矛盾, 2-of-3裁决）
├── annotation_queue.py  ← 标注队列
│                           Redis BRPOP 消费 → PostgreSQL 持久化
│                           后台消费者池（3 并发 worker）
│                           自动触发: buffer≥100 → OptimizationAgent
├── prompt_optimizer.py  ← DSPy 风格优化器
│                           PromptRegistry: 版本管理 + A/B验证 + 回滚
│                           DspyStyleOptimizer: BootstrapFewShot + Feedback优化
│                           FeedbackLoop: 收集→积累→触发→分组→优化
└── optimization_agent.py← LLM 智能优化 Agent
│                           读取错误→LLM分析→4种动作:
│                           prompt_update/keyword_update/
│                           threshold_adjust/rag_case_add
│                           → 生成报告 (before/after 对比)
```

**大白话解释**：
- **标注 Agent**：每条审核完自动"二审"——先用关键词快速检查，和模型结果一致的直接放行（省 Token），不一致的调 LLM 再判一次，最后三方投票决定模型有没有错。
- **优化 Agent**：标注发现的错误攒够了→LLM 分析"为什么错这么多？"→自己决定是改 Prompt、加关键词、调阈值还是补案例→生成新版本。

7. 返回结果给前端
8. 前端把风险分（圆环图）和违规详情展示在网页上

简单文本审核通常只需要 **1-2 秒**。

## 5. 数据从哪里来、存在哪

### 5.1 数据存储

| 存储位置 | 存什么数据 | 怎么查看 |
|---------|-----------|---------|
| **PostgreSQL** | 审核记录、策略配置、审计日志、核心记忆、账号画像、标注记录 | `psql` 命令行或数据库管理工具 |
| **Redis** | 短期任务状态、LLM 缓存、内容去重、任务队列、标注队列 | `redis-cli` 命令行 |
| **ChromaDB** | 审核案例向量（BGE-M3 嵌入）、核心记忆向量 | 持久化到 `/workspace/data/chroma` |
| **NetworkX（内存）** | 违规类型知识图谱 | 代码中通过 NetworkX API 访问 |
| **日志文件** | 管线追踪、审计日志、遥测数据 | `/workspace/logs/` 目录 |

### 5.2 数据量的直观概念

```
PostgreSQL 数据库（8 张表）：
  - moderation_records: 审核记录（持续增长，每条审核一条）
  - blackhat_patterns: 黑灰产模式（预置规则）
  - account_profiles: 账号风险画像
  - audit_logs: 操作审计日志
  - annotation_records: 自动标注记录（三方投票结果）
  - dataset_samples: 评测数据集样本
  - moderation_policies: 策略配置（敏感词/阈值/权重）
  - core_memories: 核心记忆（重要性>0.7）

Redis 缓存（5 种 key 模式）：
  - short_term:{id}: 任务状态 Hash（1h TTL）
  - cache:llm:{md5}: LLM 缓存（1h TTL）
  - dedup:{md5}: 内容去重（1h TTL）
  - task_queue: 任务队列 Sorted Set（24h TTL）
  - annotation:*: 标注队列 + buffer + stats

ChromaDB 向量库（2 个集合）：
  - moderation_cases_v2: 全部审核案例的 BGE-M3 embedding（1024维）
  - core_memory_v2: 高重要性案例的 embedding（1024维）
```

### 5.3 系统启动时的初始化流程

```
1. PostgreSQL 连接池建立（pool_size=20, max_overflow=10）
2. Redis 连接建立
3. ChromaDB PersistentClient 连接到 /workspace/data/chroma
4. GraphRAG 图谱状态从 PostgreSQL 恢复
5. 后台 TaskWorkerPool 启动（3 worker, BRPOP 消费）
6. 后台 AnnotationConsumer 启动（3 worker, BRPOP 消费）
7. API 服务启动，等待请求
```

日志是排查问题的**第一工具**。所有日志文件在 `logs/` 目录下。

### 8.1 日志文件结构

```
logs/
├── pipeline.jsonl        ← 审核管线全链路日志（每条审核一个 JSON 对象）
├── mcp_audit.jsonl       ← MCP 工具调用审计日志
├── backend.log           ← Python 模块运行日志

### 8.2 怎么查看日志

```bash
# 查看最近的审核步骤（最后 10 条）
tail -10 logs/pipeline.jsonl

# 查看最近的工具调用审计
tail -10 logs/mcp_audit.jsonl

# 查看后端运行日志（最后 50 行）
tail -50 logs/backend.log

# 实时查看 Pipeline 日志
tail -f logs/pipeline.jsonl
```

### 8.3 日志内容解读

Pipeline 日志的典型格式（每条审核一个 JSON 对象）：

```json
{
  "content_id": "mod_a1b2c3d4",
  "content_type": "text",
  "total_duration_ms": 950,
  "step_count": 7,
  "steps": [
    {"seq": 1, "node": "GATEWAY", "action": "状态初始化", "duration_ms": 1},
    {"seq": 2, "node": "🧠 SUPERVISOR", "action": "内容分类: text", "duration_ms": 5},
    {"seq": 3, "node": "🚦 TRIAGE", "action": "分诊台: tier=med risk=0.52 complexity=3",
     "output": {"tier": "med", "cost_saved": false}, "duration_ms": 1},
    {"seq": 4, "node": "🔀 LANE_ROUTE", "action": "med → text_agent (标准车道)",
     "output": {"tier": "med", "target": "text_agent"}, "duration_ms": 1},
    {"seq": 5, "node": "📝 TEXT_AGENT", "action": "文本审核完成",
     "output": {"violation_type": "advertisement", "risk_score": 0.72},
     "duration_ms": 850},
    {"seq": 6, "node": "📊 RISK_ASSESS", "action": "风险评估: REJECT",
     "output": {"decision": "REJECT", "score": 0.78}, "duration_ms": 50},
    {"seq": 7, "node": "GATEWAY", "action": "审核完成",
     "output": {"decision": "REJECT", "score": 0.78, "total_ms": 950}, "duration_ms": 1}
  ]
}
```

**关键信息解读**：
- `node`：哪个模块执行的
- `duration_ms`：这一步花了多少毫秒
- `output`：这一步产出了什么结果
- `step_count`：一共多少步

### 8.4 异常日志怎么看

如果审核出了问题，日志中会出现 `level: "WARN"` 或 `level: "ERROR"`：

```json
{"seq": 5, "node": "🔄 PLANNER", "action": "部分失败(已降级): ...",
 "level": "WARN", "duration_ms": 0}
```

**大多数 Warning 是安全的**——系统会自动降级到备选方案。比如 DeepSeek 不可用时会用规则模板兜底。

## 9. 常见问题解决

### 9.1 启动报错：端口被占用

```
Error: [Errno 98] Address already in use
```

**解决**：先停掉旧进程，再启动。

```bash
lsof -i :18080          # 查看占用 18080 端口的进程
kill -9 <进程ID>        # 杀掉进程
python -m src.backend.main  # 重新启动
```

### 9.2 数据库连接失败

```
connection refused
```

**解决**：启动 PostgreSQL，或者检查连接配置。

```bash
sudo service postgresql start
psql -h localhost -U postgres -d moderation  # 测试连接
```

### 9.3 DeepSeek API 调用失败

```
[LLM] DeepSeek API error: Authentication error
```

**原因**：API 密钥失效或网络不通。
**解决**：更新 `.env` 文件中的 `DEEPSEEK_API_KEY`。即使没有 API 密钥，文本审核功能仍可以用规则（关键词+正则）运行。

### 9.4 前端页面空白或报错

```bash
# 检查后端是否在运行
curl http://localhost:18080/health

# 检查前端控制台（浏览器 F12 → Console）
# 常见原因：后端 API 不可达、跨域配置问题（检查 CORS 设置）

# 重新构建前端
cd /workspace/src/frontend && npm run build
```

### 9.5 审核不出结果（一直在等待）

```bash
# 检查日志确认流程走到哪一步了
tail -20 logs/pipeline.jsonl

# 检查任务状态
curl http://localhost:18080/api/v1/moderate/task/{task_id}

# 可能原因：LLM 调用超时、图片分析耗时过长
```
