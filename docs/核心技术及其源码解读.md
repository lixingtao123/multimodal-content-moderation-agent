# Part 1: 基础能力层

## §1 系统全景图

### 🎯 通俗理解

这是一个**内容安全审核中台**。你可以把它想象成一个自动化内容审核工厂：

```
                    ┌────────────────────┐
  用户提交内容       │    API 网关        │  ← 接收请求的"前台"
  (文本/图/音/视)   └────────┬───────────┘
                             │
              ┌──────────────▼──────────────┐
              │     Agent 编排中心          │  ← 13 个 AI"专家"协作
              │                             │
              │  ①Supervisor → 分诊台       │  ← 入口先分诊
              │  ┌─────┐ ┌─────┐ ┌─────┐   │
              │  │组长 │ │分诊 │ │调度 │   │  Supervisor/Triage/Planner
              │  └──┬──┘ └──┬──┘ └──┬──┘   │
              │     │       │       │       │
              │  ┌──▼──┐┌──▼──┐┌──▼──────┐ │
              │  │文本 ││图片 ││音频│视频 │ │  Text/Image/Audio/Video
              │  │专家 ││专家 ││专家│专家 │ │
              │  └──┬──┘└──┬──┘└──┬─┴──┬──┘ │
              │     │       │       │    │    │
              │  ┌──▼───────▼───────▼────▼──┐│
              │  │   综合评估 + 终审        ││  Risk(含意见协商)
              │  └─────────────────────────┘│
              └──────────────┬──────────────┘
                             │
              ┌──────────────▼──────────────┐
              │       记忆与知识库          │  ← "档案室"
              │  短期记忆(Redis)            │
              │  长期记忆(PostgreSQL)        │
              │  案例库(ChromaDB向量检索)   │
              └──────────────┬──────────────┘
                             │
              ┌──────────────▼──────────────┐
              │      自动进化系统           │  ← "质检+培训"
              │  标注Agent(自动校验)        │
              │  → 优化Agent(改进Prompt)    │
              └─────────────────────────────┘
```

**最新架构要点**（与旧版的核心差异）：

1. **入口先分诊**：Supervisor 完成内容分类后，不直接分发给审核专家，而是先进入 **分诊台 (Triage)**，基于风险与复杂度估计把内容分流到**三层路由**（快车道 / 标准车道 / 专家车道），让低成本模型处理大多数普通内容，大模型只聚焦真正的难点。
2. **意见协商内嵌终审**：旧版的"辩论面板 + 反思 + 终审"三个独立节点，现在统一收敛到 **RiskAgent** 一个节点内（先收集各 Agent 意见做加权投票，再做综合风险评估），流程更短、链路更稳。
3. **反漏审三重防线**：规则命中段注入、长文本分段审核、VL 失败显式降级不静默放行（详见 §11 / §15）。

**数据流关键说明**：
- **Triage 是三层路由的"分岔口"**：它消费 ModelRouter 的判定（见 §9），把内容分成 low（快车道）/ high（专家车道）/ med（标准车道）。
- **RiskAgent 内嵌意见协商**：多 Agent 意见不一致时在 RiskAgent 内做加权投票（详见 §12），无需单独的辩论节点。
- **异步兜底**：RiskAgent 结束后 fire-and-forget 触发 FeedbackLoop / HardCaseMining / MemoryConsolidation / AnnotationAgent（详见 §16-§17）。

## §2 贯穿案例

为了帮助理解，我们将用一条真实案例贯穿全文。

**案例内容**：用户上传了一个 DOCX 文件（9,000 字的产品说明文档，内含 20 张嵌入的流程图和产品图），还有一张独立的产品宣传图，和一段 7 秒的促销语音。

**输入包**：
```json
{
  "content_type": "multi_modal",
  "text": "请审核这些推广材料是否合规",
  "files": [
    {"filename": "2.使用说明书.docx", "content": "<255KB>"},
    {"filename": "产品图.png", "content": "<607KB>"},
    {"filename": "促销录音.wav", "content": "<307KB>"}
  ]
}
```

**在系统内部发生了什么？**

```

                    │
════════════════════▼═══════════════════════════════════════════════════
API 层: _run_moderation_core()                                          ║
═══════════════════════════════════════════════════════════════════════════
```

## §3 嵌入模型 — BGE-M3

**作用**：把文本转成 1024 维向量，用于向量检索（Dense RAG）与语义缓存。

**核心实现**：`src/backend/memory/` 下的向量化服务统一封装，具备**多级回退**——优先使用 BGE-M3（多语言混合检索模型），模型不可用时降级到轻量 embedding，保证检索链路不因单点故障而中断。

```
文本 "加我微信免费领取试用装"
        │  BGE-M3 encode
        ▼
  [0.023, 0.891, ...]  ← 1024 维 float 向量
        │
        ├─→ 存入 ChromaDB (moderation_cases_v2 / core_memory_v2 集合)
        └─→ 查询时做余弦相似度召回
```

**在系统里的位置**：Dense 向量检索层（§6 第②层）的文本向量通道、文本语义缓存；图片"以图搜图"由 `multimodal_rag.py` 的 CLIP 视觉检索承担（CLIP 512 维与文本案例 1024 维不兼容时自动回退文本 RAG）。

## §4 多模态理解 — VL + ASR

系统用两个模型理解"非文本"模态：

| 能力 | 模型 | 用途 |
|------|------|------|
| 视觉理解 VL | Qwen3-VL（`qwen3.6-plus`） | 看图 + OCR 提取图中文字 + 识别二维码/可疑元素 |
| 语音转写 ASR | FunASR (SenseVoiceSmall) | 语音 → 文字 |
| 说话人识别 | 3D-Speaker (ERes2NetV2) | 多人对话场景区分说话人 |

**VL 双 Prompt 设计**：

```
普通图片:  VL_EXTRACTION_PROMPT
           "分析这个视频帧/图片是否包含违规内容(色情/暴力/政治/广告), JSON格式返回"
           → violation_type / ocr_text / scene_description / suspicious_elements

嵌入图片:  VL_CONTEXTUAL_PROMPT (注入 ±500 字上下文)
           "这张图嵌在'产品概述'和'新款运动鞋'之间,
            请结合这段文字判断图片内容和文字的关系"
           → 额外返回 text_image_relation
```

**⚠️ 防静默放行（重要）**：真实模式下 VL 客户端缺失时**禁止回退 Mock 伪造结果**，直接返回显式错误；VL 调用失败时标记 `violation_type="unknown"`、`risk_score=0.55`、`tags=["vl_unavailable"]`，确保进入人工复核而非被当成"正常内容"放过（详见 §11 ImageAgent）。

## §5 大语言模型 — DeepSeek

**作用**：文本语义违规判定、Agent 推理、优化分析等所有"深度思考"都由它完成。

- 模型名：`deepseek-v4-flash`（高吞吐 + 低延迟，长上下文支持约 1M）
- 调用方式：OpenAI 兼容接口（`AsyncOpenAI`），temperature 区分场景（主审核 0.1 保证稳定，独立复核 0.7 保证差异化）
- 上下文注入：待审核文本 + 命中段 + RAG 案例 few-shot + 核心记忆 + Skill 指令

```
LLM 调用链 (text_agent._analyze_semantic):
  system_prompt = PromptRegistry.get_prompt("text_moderation")
                + keyword-check Skill + history-search Skill
  user_message  = "{text}" + focus_block(命中段) + rag_context + memory_context
  → violation_type / confidence / reason / reasoning (JSON)
```

**缓存**：相同 Prompt 的判定结果缓存到 Redis（`cache:llm:{md5}`，1h TTL），重复内容不再重复调用 LLM。

## §6 RAG 检索增强生成 — 六层检索体系

RAG（Retrieval-Augmented Generation）让 AI 先查历史案例再判定。系统实现**六层级联检索**，从前端"技术实验室→RAG 调试"面板可以直接观察每一层的命中结果：

```
用户查询: "加我微信免费领取试用装"
    │
    ▼
 ① BM25 关键词检索 (sparse)        → 词法命中
    │
    ▼
 ② Dense 向量检索 (BGE-M3)         → 语义相似
    │
    ▼
 ③ RRF 融合 (k=60)                → 合并去重排序
    │
    ▼
 ④ CrossEncoder 重排               → 精排分数
    │
    ▼
 ⑤ Agentic RAG (改写→路由→检索→自评)
    │  QueryRewrite → HybridSearch → SelfRAG 质量评估
    ▼
 ⑥ GraphRAG (NetworkX BFS 2跳)     → 违规类型关联增强
```

**各层一句话**：

| 层 | 一句话 | 依赖 |
|----|--------|------|
| BM25 | 找包含相同关键词的历史案例 | 倒排索引（内存） |
| Dense | 找语义相近的案例 | BGE-M3 + ChromaDB |
| RRF | 两种检索结果融合排序 | 排序融合算法 |
| CrossEncoder | 深度语义精排 | 交叉编码器 |
| AgenticRAG | 自动改写查询、按需检索、质量自评 | LLM + 多轮循环 |
| GraphRAG | 关联违规类型的知识图谱扩展 | NetworkX |

**历史案例索引**：审核完成的每条记录都会 `save_case()` 写入 ChromaDB 的 `moderation_cases_v2` 集合，作为后续审核的参考依据。

## §7 MCP 工具协议 — 标准化能力调用

MCP（Model Context Protocol）让 Agent 通过统一标准调用外部能力。系统自建 `mcp_servers/` 实现 JSON-RPC 2.0 协议，注册 **8 个审核工具**：

| 工具 | 功能 | 类型 |
|------|------|------|
| `keyword_check` | AC 自动机敏感词扫描（纯本地，~1ms） | 文本 |
| `history_search` | BM25+Dense+CrossEncoder 混合检索历史案例 | 文本 |
| `image_hash` | dHash 相似图片检测（64bit 指纹 + 汉明距离） | 图像 |
| `account_risk_check` | 账号历史违规记录查询 | 文本 |
| `adversarial_detect` | 对抗文本检测（同音字/拆字/Unicode 混淆） | 文本 |
| `url_check` | 恶意 URL / 钓鱼链接检测 | 文本 |
| `content_dedup` | MD5 内容去重（Redis 缓存） | 文本 |
| `regex_rule_check` | 正则规则（手机号/银行卡/黑话） | 文本 |

**工具调用流水线**（`mcp_gateway/gateway.py`）：

```
Agent 想用 keyword_check
  → RBAC 权限检查 (access_control.py: 哪个 Agent 能用哪个工具)
  → 参数校验
  → 执行工具
  → 审计记录 (audit.py → mcp_audit.jsonl + PostgreSQL)
```

**为什么叫 MCP**：MCP 是 Anthropic 提出的 AI 工具连接标准，就像 USB 是设备连接标准一样，MCP 是 AI 和工具的连接标准。系统用 MCP 把审核能力（敏感词、检索、图像指纹）标准化，Agent 通过统一的 `_call_mcp_tool()` 调用，实现"能力与 Agent 解耦"。

## §8 Skills 知识系统 — 渐进式加载

Skill 是"怎么做好某件事"的操作指南。系统注册 **44 个 Skill**，覆盖审核策略、风险研判、对抗识别、多模态证据融合等场景。

**三层渐进式加载**（`skill_registry.py`）：

```
L1 元数据: 启动时扫描全部 name + description + mcp_tools (~100 tokens/skill)
L2 完整内容: 首次使用时加载 SKILL.md 全文 (~1000-2000 tokens/skill)
L3 按需注入: 审核时把相关 Skill 注入 system prompt
```

**审核时注入**（以 TextAgent 为例）：

```
_analyze_semantic():
  skill_context = self._load_skill_context(["keyword-check", "history-search"])
  system_prompt = f"{system_prompt}\n\n{skill_context}"
```

**核心 Skill 示例**：

## §9 Agent 全景 — 谁做什么、何时触发

### 🎯 通俗理解

把审核团队想象成一家公司，13 个"角色"各司其职：

| # | Agent / 节点 | 角色 | 什么时候干活 |
|---|-------------|------|------------|
| ① | Supervisor | 组长 | 每条审核都先经过他，看一眼内容类型，登记任务 |
| ② | Triage | 分诊台护士 | 每一条都经过他，判断"轻症/普通/重症"，分流到不同车道 |
| ③ | FastLane | 社区门诊 | 低风险内容，用本地小模型秒级判定，不占用大模型 |
| ④ | Brain | 专家会诊 | 高风险/复杂内容，先做 4 类决策再进标准链路 |
| ⑤ | Planner | 调度员 | 多模态（文档/图片/音频混合）内容，协调 5 阶段流程 |
| ⑥ | FileAgent | 档案员 | 有人上传了文档(PDF/DOCX/TXT)就出动，拆解文字和嵌入图片 |
| ⑦ | TextAgent | 文字专家 | 只要有文字就出动。最忙的 Agent |
| ⑧ | ImageAgent | 图片专家 | 有图片就出动，用视觉模型看图 + 提取图中文字 |
| ⑨ | AudioAgent | 音频专家 | 有音频就出动，语音转文字 → 文字审核 |
| ⑩ | VideoAgent | 视频专家 | 有视频就出动，抽帧 → 逐帧看图 → 提取音频 |
| ⑪ | ReAct Agent | 高级侦探 | 文字专家拿不准时（违规 + 置信度<0.6/对抗），多步推理深挖 |
| ⑫ | RiskAgent | 终审法官 | 每条审核最后都要经过他：意见协商 + 综合评分 + 终止双签 |
| ⑬ | Human-in-Loop | 人工兜底 | 高风险/低置信/意见分歧，暂停等人工判定 |

```python
def create_moderation_workflow() -> StateGraph:

    workflow.add_node("supervisor", supervisor_node)      # ① 内容分类
    workflow.add_node("triage", triage_node)              # ② 分诊台
    workflow.add_node("fast_lane", fast_lane_node)        # ③ 快车道
    workflow.add_node("brain", brain_node)                # ④ 大脑仲裁
    workflow.add_node("planner", planner_node)            # ⑤ 多模态调度
    workflow.add_node("file_agent", file_agent_node)      # ⑥ 文件解析
    workflow.add_node("text_agent", text_agent_node)      # ⑦ 文本审核
    workflow.add_node("image_agent", image_agent_node)    # ⑧ 图片审核
    workflow.add_node("audio_agent", audio_agent_node)    # ⑨ 音频审核
    workflow.add_node("video_agent", video_agent_node)    # ⑩ 视频审核
    workflow.add_node("react_agent", react_agent_node)    # ⑪ ReAct 深挖
    workflow.add_node("risk_agent", risk_agent_node)      # ⑫ 综合评估
    workflow.add_node("human_in_loop", human_in_loop_node)# ⑬ 人工兜底

    workflow.set_entry_point("supervisor")

    # ── 边配置 ──
    # Supervisor → Triage（分诊）→ 三层路由
    workflow.add_edge("supervisor", "triage")
    workflow.add_conditional_edges(
        "triage", route_after_triage,
        {
            "fast_lane": "fast_lane",
            "brain": "brain",
            "text_agent": "text_agent",
            "image_agent": "image_agent",
            "audio_agent": "audio_agent",
            "video_agent": "video_agent",
            "file_agent": "file_agent",
            "planner": "planner",
            "__end__": END,
        },
    )

    # 快车道 → END（小模型直判，无后续节点）
    workflow.add_edge("fast_lane", END)
    # 大脑 → 标准分发（决策后走现有执行管线，行为与 med 一致）
    workflow.add_conditional_edges(
        "brain", route_by_content_type,
        {
            "text_agent": "text_agent",
            "image_agent": "image_agent",
            "audio_agent": "audio_agent",
            "video_agent": "video_agent",
            "file_agent": "file_agent",
            "planner": "planner",
            "__end__": END,
        },
    )

    # 多模态路径: Planner → FileAgent → TextAgent
    workflow.add_edge("planner", "file_agent")
    workflow.add_edge("file_agent", "text_agent")

    # 各模态 Agent → ReAct / Risk (意见协商内嵌 RiskAgent)
    for agent in ["text_agent", "image_agent", "audio_agent", "video_agent"]:
        workflow.add_conditional_edges(agent, route_after_agent, {
            "react_agent": "react_agent",
            "risk_agent": "risk_agent",
        })

    # ReAct → Risk
    workflow.add_edge("react_agent", "risk_agent")

    # 人工审核 → Risk 或等待
    workflow.add_conditional_edges("human_in_loop", route_after_human, {
        "risk_agent": "risk_agent",
        "__end__": END,
    })

    # Risk → 人工审核 或 结束
    workflow.add_conditional_edges("risk_agent", route_after_risk, {
        "human_in_loop": "human_in_loop",
        "__end__": END,
    })

    # ── 编译 (MemorySaver 提供状态持久化) ──
    checkpointer = MemorySaver()
    return workflow.compile(checkpointer=checkpointer)
```

## §10 Planner — 多模态 5 阶段编排

### 🎯 通俗理解

当用户上传了"文档+图片+音频"这种混合内容，系统需要一个调度员来决定：先做什么后做什么？哪些可以并行？Planner 就是干这个的。

Planner 不用 LLM 来做决定（那太慢太贵），而是用固定的 5 步流程：

```python
# agent_moderation/workflows/moderation.py (planner_node)
async def planner_node(state: ModerationState) -> ModerationState:
    """
    Planner — 固定路线, 0 LLM 调度开销
    DAG 依赖: FileAgent → [ImageAgent(s) ‖ AudioAgent(s)] → TextAgent
              → 跨模态关联 → 输出
    """

    # ═══════════════ Phase 1: 文件解析 ═══════════════
    if files:
        file_agent = FileAgent()
        state = await file_agent.process(state)
        # DOCX 嵌入图追加到 files 后, 重新读取
        files = state["content"].get("files", []) or files

    # ═══════════════ Phase 2: 并行模态分析 ═══════════════
    # 收集图片 (独立 + DOCX 嵌入 + 直接image字段)
    all_image_infos = []
    for f in files:
        if f.get("mime_type","").startswith("image/"):
            # 嵌入图(DOCX内嵌)取±500字上下文; files里的独立图无上下文("")
            # (content["image"]直接传图才有前500字上下文, 见下方 2b 分支)
            ctx_before = combined_text[max(0, cp-500):cp] if embedded and cp else ""
            ctx_after  = combined_text[cp:cp+500] if embedded and cp else ""
            all_image_infos.append({
                "content": f["content"], "context_before": ctx_before,
                "context_after": ctx_after, "is_embedded": embedded,
                "char_position": cp,   # P2: 位置锚定, 供 Phase 3 插回文档
            })

    # 并行执行 (Semaphore(5) 限流)
    sem = asyncio.Semaphore(5)
    image_agent = ImageAgent()
    audio_agent = AudioAgent()

    all_tasks = [_process_one_image(info, sem, image_agent)
                 for info in all_image_infos]
    all_tasks += [_process_one_audio(f, audio_agent) for f in audio_files]
    all_results = await asyncio.gather(*all_tasks, return_exceptions=True)

    # 递归转纯dict, 防止 SimpleNamespace 无法被 msgpack 序列化
    image_results = [_ensure_plain_dict(r) for r in ...]
    audio_result = _ensure_plain_dict(audio_results[0]) if audio_results else {}

    # ═══════════════ Phase 3: 上下文融合 ═══════════════
    # 3a: 收集每图判定/描述片段 (char_position, is_embedded, block)
    image_judgments = [(img_r.get("char_position"),
                        img_r.get("is_embedded", False), block)
                       for img_r in image_results]

    # 3b: 位置化融合 — 嵌入图描述按 char_position 从后往前插回原文
    anchored = [(cp, txt) for cp, emb, txt in image_judgments
                if cp is not None and emb]
    standalone_blocks = [txt for cp, emb, txt in image_judgments
                         if not (cp is not None and emb)]
    if anchored:
        position_text = combined_text
        for cp, block in sorted(anchored, key=lambda x: x[0], reverse=True):
            pos = max(0, min(int(cp), len(position_text)))
            position_text = position_text[:pos] + block + position_text[pos:]
        fused_text_parts = [position_text] + standalone_blocks
    else:
        fused_text_parts = [combined_text] + [txt for _, _, txt in image_judgments]

    # OCR 段单独收集 (统计 + 跨模态关联 ④c 用), 不拼入融合文本
    ocr_texts = [f"[图片{i+1} OCR: {r.get('ocr_text','')}]"
                 for i,r in enumerate(image_results) if r.get('ocr_text')]
    asr_text = ""
    if audio_result:
        asr_text = audio_result.get("transcribed_text", "") or ""
        if asr_text.strip():
            asr_text = f"[音频转写: {asr_text}]"
    if asr_text:
        fused_text_parts.append(asr_text)
    fused_text = "\n".join(p for p in fused_text_parts if p.strip())

    # 3c: TextAgent 对融合文本做增强分析 (超长自动分段)
    text_agent = TextAgent()
    text_result_state = await text_agent.process({
        "content": {"text": fused_text}, "content_id": content_id,
        "content_type": "text", "messages": [],
    })
    text_result = _ensure_plain_dict(
        text_result_state.get("text_result") or {})

    # ═══════════════ Phase 4: 跨模态关联 ═══════════════
    cross_modal_findings = []
    # ④a 图文矛盾: text=normal + image有违规 → 图片绕过文本审核
    # ④b 图文互证: 一致 → confidence × 1.15
    for si in suspicious_images:
        if si["violation_type"] == text_vt and text_vt != "none":
            cross_modal_findings.append({
                "type": "图文互证", "severity": "info",
                "detail": f"文本+图片{si['index']}一致, 置信度提升15%"
            })
            text_result["confidence"] = min(
                text_result.get("confidence",0) * 1.15, 1.0)

    # ④c OCR融合 ④d 音频关联 ...

    # ═══════════════ Phase 5: 输出 ═══════════════
    state["text_result"] = _ensure_plain_dict(text_result)
    state["image_result"] = _ensure_plain_dict(best_image)
    state["audio_result"] = _ensure_plain_dict(audio_result or {})
    state["_cross_modal_findings"] = cross_modal_findings
    state["_planner_processed"] = True  # ← 关键! 阻止下游重复

    return state
```

### 🔬 _ensure_plain_dict — SimpleNamespace 防护

MCP 工具返回的 `SimpleNamespace` 对象（支持 `.attr` 访问）无法通过 LangGraph `MemorySaver` 的 msgpack 序列化。`_ensure_plain_dict` 递归将所有 SimpleNamespace 转为纯 dict：

```python
def _ensure_plain_dict(obj):
    """递归 SimpleNamespace → dict, list → list, 标量保持不变"""
    if isinstance(obj, SimpleNamespace):
        return {k: _ensure_plain_dict(v)
                for k, v in obj.__dict__.items() if not k.startswith("_")}
    elif isinstance(obj, dict):
        return {k: _ensure_plain_dict(v) for k, v in obj.items()}
    elif isinstance(obj, (list, tuple)):
        return [_ensure_plain_dict(v) for v in obj]
    return obj
```

### 🔬 _planner_processed 跳过机制

这是防止重复处理的核心机制。Planner Phase 5 会设置 `_planner_processed = True`，下游的 FileAgent / TextAgent 检测到后跳过，避免多模态内容被重复分析（旧版因缺少此标记，Planner 崩溃后 FileAgent 会重新解析全部文件、重复处理多轮）。

```python
# file_agent_node: 检查标记 → 跳过文件解析
if state.get("_planner_processed"):
    state["messages"].append({"role": "file_agent",
        "content": "Skipped (Planner pre-processed)"})
    return state  # ← 直接返回, 不执行文件解析

# text_agent_node: 检查标记 → 跳过核心, 仅聚合黑灰产
if state.get("_planner_processed"):
    _aggregate_blackhat_result(state)  # 只做这个
    return state  # ← 跳过 LLM 调用、RAG 检索等
```

```
        │ 是                     │ 否

```

## §12 意见协商与反思 — 多 Agent 质量保障

### 🎯 通俗理解

多个审核专家意见不一致怎么办？系统在 **RiskAgent 阶段一**内做"意见协商"（即旧版的辩论面板功能）：

- **多 Agent 意见一致** → 快速共识，直接采纳
- **多 Agent 意见不一致** → 加权投票，取多数派违规类型
- **单一 Agent 但"不确定"** → 标记人工复核
- **意见分歧且高风险** → 标记人工复核

### 🔬 协商逻辑源码（risk_agent_node 阶段1）

```python
panel = _get_debate_panel()
opinions = panel.collect_opinions(state)

if len(opinions) >= 2:
    unique_types = set(o.violation_type for o in opinions)
    if len(unique_types) >= 2:
        # 真正有分歧 → 加权投票
        debate_result = panel.debate(opinions)
        state["_debate_result"] = {
            "debated": True,
            "mode": debate_result.debate_mode.value,   # 加权投票模式
            "final_type": debate_result.final_violation_type,
            "final_confidence": debate_result.final_confidence,
            "is_consensus": debate_result.is_consensus,
            "needs_human_review": debate_result.needs_human_review,
            "opinion_count": len(opinions),
        }
    else:
        # 多个意见但类型一致 → 快速共识
        avg_conf = sum(o.confidence for o in opinions) / len(opinions)
        state["_debate_result"] = {
            "debated": False, "is_consensus": True,
            "opinion_count": len(opinions),
            "final_type": list(unique_types)[0],
            "final_confidence": avg_conf,
        }
elif len(opinions) == 1:
    # 单一 Agent 意见 → 直接采纳; 但 uncertain 需要人工
    has_uncertain = op.violation_type == "uncertain"
    state["_debate_result"] = {
        "debated": False,
        "needs_human_review": has_uncertain,
        "opinion_count": 1,
        "final_type": op.violation_type if not has_uncertain else "uncertain",
        "final_confidence": op.confidence,
        "summary": "单一Agent意见, 直接采纳",
    }
```

**协商结果 → 人工复核**：

```python
if dr.get("needs_human_review") or hr.get("required"):
    state["_human_review"] = {
        "required": True,
        "reason": dr.get("summary", "辩论升级"),
```

### 🎯 反思（Reflexion）去哪了

旧版的独立 Reflexion 节点已**合并进 ReAct 的第二阶段**：ReAct 深挖后会对结果做自校准（LLM 自评 → 修正置信度），见 §13。这样既保留了"自我检查修正"能力，又减少了图节点数量、缩短了链路。

## §13 ReAct Agent — 深度多步推理

### 🎯 通俗理解

当某个 Agent 判定内容违规、但置信度不高（<0.6）或疑似对抗样本时，系统不能直接下结论，而是派 ReAct Agent 像侦探一样多步深挖：先"思考"（Thought），再"行动"（调用工具查证），再"观察"（看结果），循环几次后给出更有把握的结论。

### 🔬 触发条件（route_after_agent）

```
result = state[text_result/image_result/audio_result/video_result]

if violation_type != "none"
   AND (confidence < 0.6 OR is_adversarial)
   AND NOT react_enhanced (尚未深挖过):
    → 进入 ReAct Agent
else:
    → 直接进入 RiskAgent
```

### 🔬 ReAct 循环结构

```
Thought: 这个文本命中"广告引流"模式, 但置信度只有 0.55。
         需要查一下历史案例确认。
Action:  history_search(query="加微信免费领取", top_k=5)
Observation: 检索到 2 条 REJECT 的广告案例, 相似度 0.83/0.79
Thought: 与历史案例高度一致, 可提高置信度到 0.85。
Action:  keyword_check(补充核查同音字变体)
Observation: 命中"加V""薇芯"等同音字变体
...（循环最多 N 轮）
Final:  violation_type=advertisement, confidence=0.85
```

完成后进入 RiskAgent 综合评估。

## §14 Human-in-the-Loop — 人工审核介入

### 🎯 通俗理解

当 AI 对某条内容拿不准时，工作流会**暂停**，把内容送入人工审核队列（PostgreSQL 持久化），等待人工标注后再继续或结束。

### 🔬 触发人工复核的三种情形

```
① RiskAgent 意见协商: Agent 判定 uncertain / 辩论升级
② RiskAssessmentAgent: REVIEW 且 0.25 ≤ risk_score < 0.70 (模糊边界)
③ RiskAgent 后: _human_review.required = True AND status = PENDING
        │
        ▼
  route_after_risk → "human_in_loop"
        │
        ▼
  human_in_loop_node: 工作流暂停
  → 人工在前端"人工审核面板"标注
  → 标注完成 status=RESOLVED
        │
        ▼
  route_after_human:
    人工采纳 → 回到 risk_agent 应用人工结论
    或直接结束
```

**⚠️ 异步模式注意**：异步审核任务中 HITL 中断不可用，任务会以 REVIEW 决策完成并留给人工在审核队列中复核（后端日志提示 "Human-in-the-Loop not available in async mode"）。

## §15 长文本处理与跨模态理解

### 🎯 双重防漏审机制

针对"违规内容藏进大段正常文本"的对抗手法，系统设计了两道防线：

**防线一：规则命中段注入（focus_segments）**

```
输入: 3000 字技术文档, 中段藏着 "加我微信 13800138000 在线裸聊"
        │
        ▼
  _extract_focus_segments(text):
    keyword_check 命中 ["微信","裸聊"] → 取命中词前后各 N 字
    → focus_block = "...部署完成后 加我微信 13800138000 在线裸聊 24小时 立即体验..."
        │
        ▼
  注入 LLM prompt:
    system: "以下是可能违规的片段, 请逐字核查是否构成违规"
    user:  focus_block + 上下文
  → 即使命中段只占全文 1%, LLM 也会聚焦核查
```

**防线二：长文本分段审核（TextChunker + ChunkResultMerger）**

```
文本长度 > 3000 字 (SEGMENT_REVIEW_THRESHOLD)?
        │ 是
        ▼
  TextChunker.chunk(text):
    CHUNK_SIZE=2000 / OVERLAP=200
    切分优先级: 段落(\n\n) > 句子(。！？!?.) > 换行(\n) > 硬截断
    只接受 > MIN_CHUNK 的切分点 (避免碎块)
        │
        ▼
  asyncio.gather 并行审核 (Semaphore(5)):
    每个 chunk 独立走 关键词→黑灰产→命中段→LLM→块级风险
        │
        ▼
  ChunkResultMerger.merge():
    violation_type: 取最高置信度非 none
    risk_score:     max(所有块) ← 保守策略, 防漏审
    confidence:     按块长度加权平均
    reasoning:      top-3 块拼接
    is_chunked:     True
```

**为什么分段？** 超长文本会稀释 LLM 注意力——违规只占全文 1.5% 时，单次审核容易漏判。分块后每块独立审查，违规即使藏在第 6 块的角落也能被抓到。实测 3378 字文本藏"加微信在线裸聊+辱骂"，分段审核成功拦截（harassment conf=0.96）。

### 🎯 跨模态理解（Planner Phase 4）

跨模态关联让"图片里的广告 + 文本里的广告 + 音频里的广告"互相印证，提升整体置信度（详见 §10 Phase 4）：

| 关联类型 | 逻辑 | 效果 |
|---------|------|------|
| 图文矛盾 | 文本判 normal 但图片判违规 | 提示图片可能绕过文本审核 |
| 图文互证 | 文本与图片判定一致 | confidence × 1.15 |
| OCR 语义融合 | OCR 段单独收集（不入融合文本）；文本判违规且有 OCR 段时记录关联 | 佐证 |
| 音频关联 | ASR 转写已并入文本分析 | 交叉校验 |

## §16 自动标注 Agent — 三方投票校验 (重点)

### 🎯 通俗理解

审核系统不是永远正确的。AnnotationAgent 像一位独立的质检员，对每个审核结果进行"二审"。它不是简单地说"对"或"错"，而是用多个独立视角交叉验证，避免"模型自说自话"。

```
审核完成 (TextAgent判定: PASS, 内容正常)
     │
     ▼
┌──────────────────────────────────────────────────────┐
│          AnnotationAgent 自动标注                     │
│                                                      │
│  视角①: 规则引擎复核 (纯本地, ~1ms)                    │
│  ┌──────────────────────────────────────────────┐   │
│  │ VIOLATION_KEYWORDS 6大类关键词                 │   │
│  │ 检查: 内容中包含 "微信""赚钱""加微信" 吗?     │   │
│  │ → 中了3个! verdict=violation                  │   │
│  │ WHITELIST 白名单检查:                          │   │
│  │ 匹配"新闻/学术/技术"? → 否                     │   │
│  │ 对抗特征: 零宽字符/异常空格? → 否              │   │
│  │ → 结论: violation (命中3个违规词)             │   │
│  └──────────────────────────────────────────────┘   │
│                                                      │
│  视角②: 工具视角复核 (MCP 工具交叉验证)              │
│  ┌──────────────────────────────────────────────┐   │
│  │ 调用 keyword_check 复核敏感词命中              │   │
│  │ 调用 history_search 检索相似历史案例           │   │
│  │ → 历史案例多为 REJECT → 佐证原判定有误         │   │
│  └──────────────────────────────────────────────┘   │
│                                                      │
│  快速跳过判断:                                        │
│  ┌──────────────────────────────────────────────┐   │
│  │ 规则引擎明确 且 与模型判定一致 → 直接判正确     │   │
│  │ → 不调 LLM (省 token, 绝大数场景命中)          │   │
│  └──────────────────────────────────────────────┘   │
│                                                      │
│  视角③: LLM 独立审核 (仅必要时, ~3s)                 │
│  ┌──────────────────────────────────────────────┐   │
│  │ 使用不同的 prompt: "你是独立审核专家"           │   │
```

```python
def _make_ruling(model_decision, model_violation_types,
                 rule_result, llm_result, contradiction_result) -> tuple:
    """三方投票裁决: 规则 + LLM + 矛盾检测, 2-of-3"""

    # 情况1: 模型判正常, 规则+LLM都认为违规 → false_negative (漏判)
    if model_says_normal:
        if (rule_says_violation and llm_says_violation) or \
           (rule_says_violation and contra_says_error) or \
           (llm_says_violation and contra_says_error):
            is_error = True; error_type = "false_negative"

    # 情况2: 模型判违规, 规则+LLM都认为正常 → false_positive (误判)
    if model_says_violation:
        if (rule_says_normal and llm_says_normal) or \
           (rule_says_normal and contra_says_error):
            is_error = True; error_type = "false_positive"

    # 情况3: 语义矛盾 → wrong_violation_type (类型错误)

    return is_error, error_type, error_detail, annotated_types, annotated_conf
```

## §18 记忆系统 — MemGPT 三层架构

审核 Agent 拥有分层记忆，像人脑一样"重要的长记，不重要的归档"：

| 层级 | 存储 | 生命周期 | 内容 |
|------|------|---------|------|
| **Core** | PostgreSQL | 永久 (MAX_EVENTS=100) | 重要性 > 0.7 的关键审核决策、高频模式 |
| **Working** | Redis + 本地 dict | 1 小时 TTL | 当前审核会话上下文、Agent 中间结果 |
| **Archival** | ChromaDB 向量库 | 永久 (检索权重 ×0.5) | 低重要性压缩摘要 (≤200 字符, 每10条批量写) |

### 🔬 重要性评分器

```python
class ImportanceCalculator:
    def calculate(self, violation_type, confidence, risk_score,
                  is_adversarial, is_first_occurrence, frequency):
        importance = type_severity            # HIGH=0.4 / MEDIUM=0.25 / LOW=0.1
        importance += confidence * 0.2        # 置信度贡献 (max 0.2)
        importance += risk_score * 0.15       # 风险分贡献 (max 0.15)
        if is_adversarial:    importance += 0.15   # 对抗样本加分
        if is_first_occurrence: importance += 0.05 # 首次出现
        if frequency >= 5:    importance += 0.05   # 高频模式
        elif frequency >= 3:  importance += 0.03
        return min(importance, 1.0)
```
